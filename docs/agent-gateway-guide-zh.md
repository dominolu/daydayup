# Safuno：融合脱敏的个人 AI 代理网关

> **对标**：[CC Switch（farion1231/cc-switch）](https://github.com/farion1231/cc-switch) · [Magpie（yetone/magpie）](https://github.com/yetone/magpie/blob/main/README.zh-CN.md)
> **对象**：本仓库 Safuno（Go 标准库实现，单二进制网关）
> **撰写日期**：2026-10-19
> **一句话**：CC Switch 管"**配置**在哪切"，Magpie 管"**流量**去哪走"，Safuno 在前两者的位置上多管一件事——"**什么内容可以出网**"。

---

## 1. 先厘清三者的位置

三者的名字看起来重叠，实际站在数据通路的不同层。把它们画在同一条链上就一目了然：

```
   Agent（Claude Code / Codex / DSH / OpenCode / Cline …）
        │
        │  ① 配置文件指向谁   ← CC Switch 的主战场（改 JSON/TOML，切换供应商）
        ▼
  ┌─────────────────────────────────────────┐
  │  ② 本地网关 / 反向代理                    │ ← Magpie 的主战场（协议互译、账号池、限额、账单）
  │  ┌───────────────────────────────────┐   │
  │  │ ③ 内容理解层                       │   │ ← Safuno 的差异化（脱敏 / 还原 / 危险工具防护）
  │  └───────────────────────────────────┘   │
  └─────────────────────────────────────────┘
        │
        ▼
   多条上游：官方 API / WorkBuddy·CodeBuddy 订阅 / SenseNova / 其它订阅账号
```

| 层 | 解决的问题 | CC Switch | Magpie | Safuno |
|---|---|---|---|---|
| ① 配置层 | 每个 Agent 的配置格式不同，换供应商要手改 | **核心**：90+ 供应商预设、一键切换、托盘切换 | 有（Agents 页模型选择器 + 方案） | 有（Agent 接入页，5 个内置 Agent） |
| ② 网关层 | 协议、账号、限流、额度、计费 | 有（本地路由 + 故障转移 + 聚合，v4 起） | **核心**：路由组、插件、Key 限额、计费 | **核心**：账号池、轮询/冷却/等待、三协议桥、额度观测 |
| ③ 内容层 | 发出去的东西里有没有不该出网的 | 无 | 无 | **核心**：出网前掩码、返回时还原、映射审计 |

> **结论先行**：CC Switch 和 Magpie 都默认"请求内容原样转发"。Safuno 的定位是在**同样做好配置与网关的前提下，把"内容"变成可治理的第三层**——这就是标题里的"融合了脱敏功能"。

## 2. 对标 CC Switch：配置层要"轻、准、可回退"

CC Switch 是 Tauri 2 桌面应用（Rust 后端），定位"Claude Code、Codex、Gemini CLI、OpenCode 等十个工具的 All-in-One 管理器"。它对配置层的三条经验值得直接继承：

1. **只改关键字段**：切换时只替换地址、Key、模型，插件、Hook、MCP 与注释原样保留；
2. **第一次改写前自动备份**，并提供"恢复官方登录"这条退路；
3. **切换成本要低到一次点击**：主界面、系统托盘、项目切换器三个入口。

Safuno 的 Agent 接入页（M1）已按同样思路实现，差异集中在"谁是改写的执行者"：

| 能力 | CC Switch | Safuno 现状 | 说明 |
|---|---|---|---|
| Agent 覆盖 | 10 个工具（含 Gemini CLI、Grok Build、OpenClaw） | 5 个：DSH、OpenCode、Claude Code、Codex、Cline | 见 README「Agent 接入」 |
| 写入方式 | 桌面 GUI，直接改本机配置 | 管理台（Web）在**网关本机**改配置 | 单机自用前提；跨机器需自行搬运 |
| 只改关键字段 | 是 | 是（保留注释、顺序、无关字段） | 原子写入 + diff 预览 |
| 备份与还原 | 自动备份、恢复官方 | 写入前备份，一键还原 | 还原后与写入前逐字节一致 |
| 漂移检测 | — | **有**：被外部工具改动后标记"配置漂移"并拒绝覆盖 | 比"静默覆盖"更稳 |
| 写入后自检 | — | **有**：确认模型在目录中 + 发一个 `max_tokens=8` 最小请求 | 失败不覆盖原配置 |
| 方案 / 项目快照 | 项目切换器（供应商+MCP+Skills+提示词） | 方案（Profiles）：各 Agent 模型选择快照，一键整套切换 | Safuno 的"方案"是**纯模型快照**，不含凭证与白名单 |
| 托盘快捷切换 | 系统托盘 | macOS 第一版有菜单栏壳；Windows/Linux 后续 | 打开管理台、复制 Base URL / Key、退出 |
| MCP / Skills / 提示词统管 | 有 | 无 | 明确不在本项目范围 |
| 供应商预设库 | 90+ 预设 | 无预设；上游是自持账号 | 本项目不对外售卖，不需要"供应商货架" |

**从 CC Switch 借来、但 Safuno 要做得更狠的一点**：CC Switch 的配置改写发生在**用户桌面**，Safuno 的改写发生在**网关侧**——这意味着 Safuno 能在"写入"与"请求实际发出"之间插一层内容治理，CC Switch 做不到。

## 3. 对标 Magpie：网关层要"不换 Agent、不换流程"

Magpie 的定位是"所有 Agent 的模型，一处搞定"：本机一个网关（`127.0.0.1:3425`），同时讲 OpenAI Chat、Responses、Anthropic Messages、Gemini 四种协议并互相转换，账号池用尽自动切下一个。详细拆解见 [magpie-analysis-zh.md](magpie-analysis-zh.md)，这里只列与本定位直接相关的部分：

| Magpie 能力 | Safuno 现状 | 落点 |
|---|---|---|
| 协议互译（Chat ↔ Responses ↔ Messages） | **已实现**（`bridges.messages` / `bridges.responses`，默认关闭） | `internal/gateway/bridge*.go` |
| 账号池轮询、冷却、用尽切换 | **已实现**，此外有有界等待队列与恢复节流 | `internal/pool` |
| 路由决策可视化 | **已实现**：路由页展示"请求→尝试链→原因→等待" | `internal/gateway` 环形记录 |
| 用量与花费 | **部分**：按客户端/模型/账号聚合 token，按价格表估算花费，无价标"未计价" | 不给无价模型编数字 |
| 额度窗口 | **部分**：带观测时间的余额快照 + 可选外部 Feed + 每日护栏 | 不把 Token 换算成官方余额 |
| 网关中间件插件 | **部分**：脱敏与工具防护是"内置中间件"，未做热插拔 | 先做对，再做可插拔 |
| Key 限额、命名 Key、局域网共享 | **无** | 单机单用户，非目标 |

Magpie 给 Safuno 的启示只有一句：**让用户不必改 Agent 的工作方式**。Safuno 沿用了这条，并且把同样的克制用在脱敏上——见下一节。

## 4. 融合点：为什么"脱敏"必须长在网关层

如果把"脱敏"做成一个独立工具（比如发消息前手动跑一遍脚本），它有四个绕不过去的问题：

1. **位置不对**：真正需要保护的是"出网的请求"，而不是"用户复制粘贴的那段文字"；只有卡在出口处才拦得住工具参数、系统提示、上下文里的敏感信息。
2. **看不到全貌**：Agent 的请求体是 JSON 套 JSON（工具参数是字符串里再套 JSON），独立工具很难正确处理嵌套。
3. **流式还原难**：模型的回复是 SSE 流，占位符会被切在两个事件之间；脱离协议做不了正确还原。
4. **不可审计**：没有"哪条原文被换成了哪个占位符、又在什么时候还原"的凭据，出了问题说不清。

Safuno 把脱敏放在**网关请求流水线的出口**，这正是 CC Switch（只管配置）和 Magpie（只管转发）都不做的那一层。请求处理顺序（`internal/gateway/server.go`）：

```
客户端请求
   │
   ├─ 1. 鉴权、限额、大小检查
   ├─ 2. 脱敏掩码（JSON / 文本）   ← 出网前最后一站
   ├─ 3. 会话归档（存的是掩码后的正文，不含原文）
   ├─ 4. 协议桥转换（Messages/Responses → Chat）
   ├─ 5. 账号池调度、等待、重试
   │
上游响应（SSE 或 JSON）
   │
   ├─ 6. 协议桥反向转换回客户端协议
   └─ 7. 占位符还原为原文，返回客户端
```

关键性质：

- **掩码在归档之前**：会话归档、请求正文下载、日志里都**不会**出现原文；
- **掩码在桥接之前**：无论客户端讲哪种协议，进入桥接的已是干净内容；桥接不额外引入明文路径；
- **还原在协议还原之后**：按客户端自己的协议（Chat choice / Messages content block / Responses output item）逐通道还原，跨事件分片会缓冲拼接；
- **工具参数单独还原**：工具调用参数里的占位符按完整 JSON 收齐后还原，再发参数增量；发现未解析占位符时**中止该工具调用**，而不是把损坏的调用交给客户端。

## 5. 脱敏能力一览（可直接对账）

| 维度 | 现状 | 证据位置 |
|---|---|---|
| 占位符形态 | `{{LABEL_6位无元音随机后缀}}`，同一原文同作用域稳定映射 | `internal/redact/placeholder.go` |
| 内置规则 | **25 条**：密钥类（API Key、云厂商 Access Key、AWS Secret、JWT、Bearer、凭据赋值、连接串、Basic Auth、Cookie、URL 查询凭据、PEM 私钥）+ PII 类（手机、座机、邮箱、身份证、银行卡 Luhn、IBAN、USCC、车牌、港澳通行证、MAC、公网 IPv4、私网 IPv4、内网 IPv4、私网 IPv6） | `internal/redact/rules.go` |
| 中文关键词 | 密码 / 口令 / 令牌 / 密钥 / 凭据 / 私钥 / 授权码… | 同上 |
| 语义校验 | 身份证校验位、银行卡 Luhn、手机号段、IP 段合法性等，降低误伤 | `internal/redact/validators.go` |
| 自定义 | `disabled_rules` 关闭单条规则；`custom_words` 增加字面词或 `re:` 正则；管理台热更新 | 管理台「脱敏」页 |
| 映射存储 | AES-256-GCM 加密，密钥来自环境变量或自动生成的 `.key`（0600） | `internal/redact/store.go` |
| 流式处理 | SSE 逐通道增量还原，CRLF、多行 data、跨事件分片 | `internal/observe/stream.go` |
| 失败策略 | `fail_closed=true`（默认）：无法安全掩码就拒绝请求，绝不透传明文 | `internal/gateway/redaction.go` |
| 审计 | 每条掩码/还原输出一条 `redaction span` 日志（规则、占位符、原文、`request_id`） | 见 README「脱敏映射日志」 |
| 危险工具防护 | `observe` 模式：识别 `rm -rf`、`base64 -d\|sh`、`curl\|sh`、fork bomb 等并计数 | `redact/tool_json.go` |
| 边界 | multipart、二进制、图片原样透传，不识别其中内容 | README「隐私脱敏层」 |

**它解决的问题（举三个真实场景）**：

1. **把生产日志贴给模型排障**：`user=admin password=***` 这类行在出网前被替换，模型仍能分析上下文，返回时再还原；
2. **Agent 自动读取 `.env` 后回显**：Key、JWT 被替换成占位符，答案里的占位符在客户端还原，看起来和没开脱敏一样；
3. **客户数据进了测试样例**：身份证、手机号、银行卡只以占位符形式到达上游。

**它不解决的问题（必须说清楚）**：

- 不改变上游**是否留存**请求——脱敏减少的是"明文外泄面"，不是"零留存"的承诺；
- 不识别图片、附件里的敏感内容；
- 不能替代组织的合规流程与数据出境评估。

## 7. 典型使用姿势

### 7.1 让 Claude Code 走自己的账号池，并且脱敏

```bash
# 1. 开启协议桥与脱敏（Claude Code 讲 Anthropic Messages，上游讲 Chat）
#    config.json: {"bridges": {"messages": true}, "redaction": {"enabled": true}}
#    脱敏规则与管理台配置可热更新；这里新增的是必填字段，用 make restart 让新配置生效
make restart

# 2. 管理台 → Agent 接入 → Claude Code → 选择模型 → 预览 diff → 写入 → 自检
#    网关会写入 ~/.claude/settings.json 的 env.ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN 与 model
```

之后 Claude Code 的每一次请求：先脱敏、再归档（存掩码版）、再桥接、再进账号池；回复逐通道还原。若想回退，点"还原"即可。

### 7.2 用"方案"在省钱/专注之间整套切换

管理台中创建"省钱"（便宜模型）与"专注"（强模型）两套方案，每套记录各 Agent 的模型选择。切换时网关先对全部 Agent 预检（漂移、不可生成则整体中止），再逐个写入；任一失败会尽量回滚已切换的 Agent，不留下半套配置。

### 7.3 核对某条敏感信息去了哪里

```bash
rg '"msg":"redaction span"' data/gateway.log | rg '3f6e...'
# masked   : 原文 → {{EMAIL_...}}
# restored : {{EMAIL_...}} → 原文
# 用同一个 request_id 对照请求日志与上游尝试日志
```

## 8. 与两者的边界（明确不做）

| 不做 | 原因 |
|---|---|
| 对外售卖、多租户、每客户计费 | 上游多为商业客户端，对外售卖账号池违反其服务条款 |
| 局域网共享、远程网关、云同步 | 单机单用户，无多设备需求 |
| MCP / Skills / 提示词统管 | 已有成熟工具（CC Switch 等），本项目聚焦网关与内容治理 |
| 托盘、菜单栏、桌面 App | 已纳入第一版 macOS 桌面壳；Windows/Linux 后续按同一架构扩展 |
| Gemini 协议桥 | 个人不使用 Gemini CLI，优先级低（见 PRD 决策 3） |
| 声称"零数据外泄" | 脱敏只减少明文外泄面，上游留存策略不受本网关控制 |

## 9. 取舍说明：单二进制与桌面壳并存

CC Switch 选择做**桌面应用**，收益是体验（托盘、项目切换器、一键升级），代价是与操作系统强耦合、需要跨平台打包。Magpie 选择做**本机网关 + 菜单栏**，收益是协议灵活，代价是要维护进程与端口。

Safuno 仍然保留**单二进制 + 内置 Web 管理台**作为服务端形态：

- 一个文件即可部署（含 Docker 镜像），CLI 和服务器不依赖桌面运行时；
- 管理台与 API 同端口，安全边界清晰（管理 Key 只存内存，不落 localStorage）；
- 脱敏、归档、计费都在同一进程内，不存在"组件之间传明文"的缝隙。

桌面 App 是**分发层**，不是重写：第一版 macOS 用 Wails v3 提供窗口、菜单栏和进程生命周期，Dashboard 直接加载网关自己的 `/admin/`，因此前端、CSP 和复制出来的 Base URL 都不变。代价是需要维护打包、签名、公证和平台集成；Windows/Linux 壳后续按同一 `internal/app` 生命周期扩展。

同步和多端仍然是明确非目标。
